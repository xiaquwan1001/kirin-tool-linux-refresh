Fork build of Kirin Tool for Linux 2.4.20 (downstream of Redminote11tech/kirin-tool-linux).

One-line: the write path now asks the device who it is and refuses to guess which device it is —
before any irreversible command goes out. Four hardenings, all from the 2026-11-15 audit of an
orphaned `fastboot oem dump-emmc ptable` that ran on a neighbouring project's phone.

Why: the incident (`/home/xuqianhui/P40pro/docs/logs/审计-2026-11-15-脚本孤儿fastboot与串号匹配.md` §4)
- 17:41, a GUI rescue flow with no `-s` sent `fastboot oem dump-emmc ptable` to the phone that the
  y700 project had in fastboot mode (another project's device), because fastboot picks "the first
  device" when nothing pins one.
- The same flow *did* record `getvar product` / `serialno`, but both were parsed as the literal
  string `OKAY`; nothing treated that as evidence, so the rescue write plan still ran.
- After the GUI exited, that fastboot child kept running for four more minutes as an orphan.

What changed (K6/K7 + two follow-ups)
1. **Pre-write identity gate (K6).** New `Services/DeviceIdentityGate.cs`: a `getvar product` answer
   that is not a model name (`OKAY`, `FAILED`, `unknown`, no `product:` line at all) now refuses the
   write with verdict `device-identity` in a `write.identity` op. `FastbootClient` gates every
   irreversible call (`flash`, `flash oeminfo`, `getvar nve:SN@…`, `erase frp`, the four
   `oeminfoerase-*`, `oem unlock`) once per client and caches the verdict. A probe that could not run
   at all (no device, stub binary, timeout) is recorded as *unreadable* and does not block: the gate
   rejects obvious nonsense, it is **not** a chip whitelist, so hisi980/hisi990/hisi9000 model name
   handling is untouched. `PreOpBackup` now records the same verdict in its op and manifest
   (`identity.refused`), and the CLI turns a refusal into `exit 3 / applied=false / reason=device_identity_refused`
   instead of an unhandled exception.
2. **VCOM port uniqueness (K7).** `LinuxSerialPortFinder.FindPort` groups candidates by their physical
   USB device (nearest sysfs ancestor with `idVendor`/`idProduct`) before choosing. Four `ttyUSB0..3`
   interfaces of one phone still count as one device (GUI behaviour unchanged); two physical devices
   with the same VID/PID now throw `AmbiguousSerialDeviceException` naming both devices and telling
   the operator to pass `--port` or unplug the other one. No change to `VcomFlasher` wire behaviour
   (its frozen hash is unchanged).
3. **Explicit `-s <SN>`.** When a target serial is configured (`KIRIN_SERIAL` > `ANDROID_SERIAL` >
   `P40_SERIAL`, `Utils/DeviceSerial`), `ProcessRunner` now writes `-s <SN>` into the child command
   line (before the subcommand) for fastboot/adb, not only into `ANDROID_SERIAL`. The op-log `argv`
   and `kirintool_log_*` now show which phone was targeted; `devices`/`--version`/help stay unpinned so
   enumeration still sees every device, and op names still come from the subcommand (`fastboot.flash`),
   never from the injected serial.
4. **Same-class review.** `FastbootClient` exposes `ExecutablePath`/`IsSystemFastboot`; a write that
   falls back to Google platform-tools `/usr/bin/fastboot` now records a warning in the diagnostics
   log before the first irreversible command. The existing multi-device refusal (`ProcessRunner`,
   `verdict=device-selection`) and the process-tree kill on host exit stay in place — that pair is what
   removes the "GUI exits, fastboot keeps writing" shape.

Verification (no hardware was touched)
- `dotnet build -c Debug`: 0 errors; `dotnet build KirinTool.Cli/KirinTool.Cli.csproj -c Release`: 0 errors.
- `tests/suites.txt`: 25/25 harnesses exit 0. `tests/WriteGates` grew 70 → 90 checks (K6 unit + e2e
  refusal, explicit `-s`, VCOM uniqueness on a fake sysfs tree), `tests/Kirin9000` 48, `tests/OpLogging`
  163, `tests/StableParity` 35 (no frozen file was modified, so no hash refresh was needed).
- The stubs that imitate a loader now answer `getvar product` like a real one; a new `bad-product`
  mode imitates the 2026-11-15 loader and asserts the write is refused.

Known gaps
- `oem dump-emmc …` is a read; the identity gate covers writes only. Wrong-device dumps are still
  prevented solely by the "no pinned serial + more than one fastboot device" refusal.
- Window close still does not *cancel* a running operation; it relies on the process-exit kill tree.
  Explicit cancellation on close is a separate change (see docs/audit/2026-11-15/round3.md TODO).
