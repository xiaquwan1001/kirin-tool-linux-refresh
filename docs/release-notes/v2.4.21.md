Fork build of Kirin Tool for Linux 2.4.21 (downstream of Redminote11tech/kirin-tool-linux).

One-line: the GUI's pre-op backup now uses the fastboot client that is actually installed in the
window at the time of the call, so a replaced client (tests, diagnostics) is honoured and a
"no device" harness can no longer spawn the real fastboot binary.

Why: 2.4.20 closed the write-path side of the 2026-11-15 incident
(`/home/xuqianhui/P40pro/docs/logs/审计-2026-11-15-脚本孤儿fastboot与串号匹配.md` §4). One root cause
was left open: `MainWindow` built `FastbootFlasherService` once in its constructor from the then
current `_xmlFastbootClient`, and everything that replaced the field afterwards (every headless GUI
harness, and the incident reproduction) still drove the *captured* client — i.e. the real bundled
fastboot. That is how a harness that by design must not contact hardware reached a neighbouring
project's phone.

What changed
- `MainWindow.RunPreOpBackupAsync` now constructs `new FastbootFlasherService(_xmlFastbootClient)` per
  call. In production this is the same object graph as before (the field is initialised in the
  constructor); for tests/diagnostics the current field wins. Backup partitioning, dump commands,
  per-partition timeout and retry behaviour are unchanged — the change is client selection only.
- `tests/StableParity/boundary.json`: `MainWindow.axaml.cs` hash refreshed with the reason recorded in
  its `reference` string (device handlers, wire commands, timings and retries untouched).

Verification (no hardware was touched)
- `dotnet build -c Debug`: 0 errors; `dotnet build KirinTool.Cli/KirinTool.Cli.csproj -c Release`: 0 errors.
- `tests/suites.txt`: 25/25 harnesses exit 0 (WriteGates 90 checks, Kirin9000 48, OpLogging 163,
  SurfaceParity 413, StableParity 35 with the refreshed hash, PreOpBackup, ApprovalGate all green).

Known gaps (unchanged from 2.4.20)
- Wrong-device *reads* (`oem dump-emmc`) are still only prevented by the "no pinned serial + more than
  one fastboot device" refusal.
- Window close still does not cancel a running operation; it relies on the process-exit kill tree.
