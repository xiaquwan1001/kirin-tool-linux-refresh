Fork build of Kirin Tool for Linux 2.4.22 (downstream of Redminote11tech/kirin-tool-linux).

One-line: the fixes that closed the write path now cover the read path too — a dump is refused when
the phone cannot name itself, a window that closes kills the fastboot it started, Windows picks a
device by physical USB device instead of the first COM port, and a fallback to the system fastboot
is a field of the result, not a line in a log file.

Why: 2.4.20/2.4.21 closed the write half of the 2026-11-15 incident
(`/home/xuqianhui/P40pro/docs/logs/审计-2026-11-15-脚本孤儿fastboot与串号匹配.md` §4). Four gaps were
left and are the TODO list in `docs/audit/2026-11-15/round3.md` §6:
- `oem dump-emmc`/`oem dump-storage` write files on the host and had already been sent to the wrong
  phone, but only *writes* were identity-gated;
- closing the GUI cancelled nothing: only host-process exit killed a child, which is how a fastboot
  stayed alive for four minutes after the window was gone;
- the Windows VCOM lookup still took "the first COM port" (K7 only fixed Linux);
- falling back to `/usr/bin/fastboot` was reported only in `kirintool_log_*.log`.

What changed (R1–R4, see `docs/audit/2026-11-15/round4.md`)
1. **Read-side identity gate (R1).** `FastbootClient.EnsureReadableIdentityAsync()` shares the cached
   `getvar product` probe with the write gate but uses the weaker rule the audit asks for: an *invalid*
   answer (the loader answered, it is not a model name — the 2026-11-15 bare `OKAY`) refuses the
   command with verdict `device-identity-read` in a `read.identity` op; an *unreadable* probe (no
   device, stub, timeout, non-zero exit) still proceeds. It covers `oem dump-emmc`, `oem dump-storage`
   and `fetch`. `PreOpBackup` judges the device *before* it creates the backup directory, so a refusal
   returns `attempted=false` with an explicit error and leaves no directory, no dump file and no
   manifest. The write gate's behaviour is unchanged (it now reuses the same cached probe).
2. **Close cancels the operation (R2).** New `Services/OperationCancellation`: every GUI operation's
   `CancellationTokenSource` is registered, and `MainWindow.Closing` cancels them all. `ProcessRunner`
   links every child to the same switch, so a close kills the fastboot process tree (3 s grace) and
   records `verdict=cancelled` instead of a timeout or an exit code. A child is never launched after a
   close has started. The dump progress dialog now says "cancelled" instead of "completed with errors";
   `FastbootFlasherService` lets the cancellation through rather than turning it into "Dump failed".
   Device commands, order, timings and retries are untouched (frozen hash refreshed with the reason).
3. **Windows port uniqueness (R3).** New `Utils/WindowsSerialPortFinder`: candidates are grouped by
   their physical USB device (parent id when known, otherwise the PNP device id without `&MI_xx` and
   the per-interface instance tail). One phone with several COM interfaces still yields its first port;
   two phones with the same VID/PID throw the same `AmbiguousSerialDeviceException` K7 introduced on
   Linux, naming both devices and suggesting `--port`. `VcomFlasher.FindWindowsPortByVidPid` is now a
   one-line delegation; Linux behaviour, wire bytes and timings are unchanged. The enumeration is an
   injectable seam because Windows cannot be run on this host.
4. **Fastboot fallback in the result (R4).** The shared JSON writer (`CliContext.WriteJson`) adds a
   top-level `degraded` array (empty when nothing is degraded) plus `fastboot.fallback=true` inside the
   `fastboot` object (`info`/`doctor`) or `fastbootFallback=true` elsewhere — so every CLI command and
   every MCP tool result (`structuredContent` and text) says when the binary in use is not the bundled
   Huawei client. Existing fields are unchanged; nothing was removed.

Verification (no hardware was touched; the P40 and the y700 were busy with other sessions)
- `dotnet build -c Debug`: 0 errors; `dotnet build KirinTool.Cli/KirinTool.Cli.csproj -c Release`: 0 errors.
- `tests/suites.txt`: 25/25 harnesses exit 0. `tests/WriteGates` 90 → 114 checks (read gate with a
  stub that logs its own argv, Windows grouping with fake PnP data, degraded flag), `tests/Kirin9000`
  48 → 52 (a stub dump that sleeps 300 s, window closed, child tree gone in 0.2 s, dialog says
  cancelled), `tests/McpProtocol` 14 → 17 (degraded token in the MCP result), `tests/StableParity` 35
  with the refreshed `MainWindow.axaml.cs` and `Services/VcomFlasher.cs` hashes, `tests/PreOpBackup`,
  `tests/FastbootReads`, `tests/OpLogging` (163) and `tests/SurfaceParity` (413) green.

Known gaps
- The Windows grouping is asserted on fake PnP data only; a real two-phone enumeration on Windows is
  still unverified (see the TODO in `docs/audit/2026-11-15/round4.md` §6).
- A loader that answers `getvar product` with a non-zero exit is "unreadable" and therefore allowed,
  by design (same trade-off as the write gate).
- USB-update and testpoint services still rely on the host-exit kill; only `ProcessRunner` (fastboot/adb)
  children are linked to the close switch.
